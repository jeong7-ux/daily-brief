GitHub Actions의 schedule 트리거가 하루 한 번 러너를 깨우고, Python 수집기가 arXiv와 RSS 7개 소스를 훑어 마크다운으로 정리한 뒤 텔레그램 봇으로 밀어 넣습니다. 서버도, 켜 둔 PC도 필요 없습니다.

cron '20 21 * * *' UTC Python 3.12 feedparser requests PyYAML Telegram Bot API ubuntu-latest
01 — 실행 흐름

워크플로가 밟는 여섯 단계

번호는 실제 실행 순서입니다. 각 단계는 앞 단계가 성공해야만 돌아갑니다 (마지막 알림 단계만 예외로, 실패했을 때만 켜집니다).

  1. 1

    트리거 — 러너 기동

    GitHub이 예약 시각에 ubuntu-latest 러너를 띄웁니다. 수동 실행 입력도 열어 두어 테스트할 때 스케줄을 기다릴 필요가 없습니다.

    scheduleworkflow_dispatchconcurrency: daily-brief
    # 21:20 UTC = 06:20 KST — 지연을 감안해 목표보다 10분 앞당김
schedule:
  - cron: '20 21 * * *'
  2. 2

    환경 구성

    저장소를 체크아웃하고 Python을 설치합니다. pip 캐시를 켜 두어 매일 같은 의존성을 다시 내려받지 않습니다.

    actions/checkout@v7actions/setup-python@v7cache: pip
  3. 3

    수집 — 7개 소스 병합

    sources.yml을 읽어 소스를 순회합니다. feedparser에 URL을 직접 주지 않고 requests로 받아 넘기는데, 일부 언론사가 기본 User-Agent를 막고 타임아웃 제어도 이쪽이 확실하기 때문입니다.

  4. 4

    렌더링 — 두 갈래 출력

    같은 데이터를 목적이 다른 두 형태로 만듭니다. 보관용은 전부 담고, 전송용은 읽기 좋게 줄입니다.

    render_markdown()render_telegram()chunk_message()
    보관용 Markdown briefs/YYYY-MM-DD.md 전 항목 + 요약문 포함
    전송용 HTML 섹션당 8건 + “외 N건” 3,500자 단위 청크 분할
  5. 5

    전송 — 텔레그램 봇

    sendMessage를 청크 수만큼 호출합니다. 텔레그램 한도는 4,096자라 줄 경계를 지켜 자르는데, HTML 태그가 중간에 끊기면 전송 자체가 거부되기 때문입니다.

    parse_mode: HTMLsecrets 주입호출 간 1초 간격
  6. 6

    커밋 — 상태 영속화

    브리프 파일과 중복 기록을 저장소에 되돌려 씁니다. 스케줄이 밀려 다른 실행과 겹칠 때를 대비해 rebase 후 push합니다.

    contents: writegithub-actions[bot]pull --rebase --autostash
02 — 시간 설계

실행 주기보다 수집 창을 넓게 잡은 이유

하루 한 번 도는데 정확히 24시간만 훑으면, 크론이 30분 밀리는 순간 그 30분치가 영구 누락됩니다. 그래서 창을 일부러 겹치게 했습니다.

arXiv만 72시간인 건 검증 중에 발견한 문제 때문입니다. 26시간 창으로는 0건이 나왔는데, 가장 최신 논문조차 29시간 전이었습니다. arXiv는 제출 마감·공지 스케줄 탓에 하루 이상 지연되고 주말에는 공지가 아예 없습니다.

03 — 필터 체인

항목 하나가 통과해야 하는 세 관문

창을 넓힌 대가로 같은 기사가 반복해서 걸립니다. 그걸 막는 게 두 번째 관문입니다.

기록 정리 save_seen() 30일 지난 항목을 버려 파일이 무한정 커지지 않게 합니다.
키워드 sources.yml 제목·요약에 부분 문자열 매칭(대소문자 무시). 비워 두면 전부 통과.

04 — 실패 처리

전송과 상태 기록을 묶어 둔 이유

seen.json을 먼저 갱신하고 전송이 실패하면, 그 항목들은 영영 오지 않습니다. 그래서 순서를 뒤집었습니다.

전송 성공

  • seen.json에 링크 기록
  • 브리프 마크다운과 함께 커밋·푸시
  • 종료 코드 0

전송 실패

  • seen.json을 갱신하지 않음 — 다음 실행에서 재시도
  • 종료 코드 1로 워크플로를 실패 처리
  • 텔레그램으로 실패 알림 + 실행 로그 링크 발송

실패 알림을 따로 둔 건, 수집기가 조용히 멈추면 브리프가 안 온다는 걸 며칠 뒤에야 알게 되기 때문입니다. 토큰이 없으면 알림 단계는 스스로 건너뜁니다.
